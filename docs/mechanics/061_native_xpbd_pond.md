## Contract

## Resources and lifecycle
- Level: `resources/levels/test_native_xpbd_pond.tres`; visible/test catalog entry.
- Independent tuning: `resources/native_xpbd_pond_physics.tres`; original XPBD values copied without retuning. Stage 60 stays Quark.
- Modular `native_xpbd_pond_handler.gd` attaches `native_xpbd_pond_layer.gd`, which inherits the reference solver and overrides numerical kernels only.
- Cleanup restores rigid integration, collision shapes/masks, visuals and removes the generated silhouette through the original cleanup.
- Native Windows x64 extension is separate from Quark. Without its class, the stage runs the GDScript solver, including on mobile.
- Pair inputs/masses are imported once per substep into C++ `PairState` records. Contact normals, six-point weights, mass denominator and approach-motion allowance are cached after first exact contact, rather than re-reading manifold Dictionaries each iteration. Gameplay contact records are emitted once per pair per substep; the exported manifold Dictionary stays available to the existing damping/energy code. Contact discovery/resolution order, force integration and iteration count stay unchanged. Remaining point/state and wall data still use Dictionaries; this is not a complete typed-state port.
- User-requested reduced collision outline: `collision_outline_stride = 2` in `native_xpbd_pond_physics.tres` selects an even sample count and samples uniformly by original perimeter length. Original six control points, 15 rest-length constraints, rest area, dense visual meshes and stored envelope radius remain intact. Pair collision polygon/guide use coarse sampling; wall contacts and pair force distribution use the full original support patch. `1` restores full collision sampling. Initial every-other sampling (17 vertices) was replaced after reported jitter; current 1–6 pair-query polygons have 16 vertices. Native-unavailable fallback retains the full reference outline. This changes collision approximation and can slightly change motion.
- Native-layer candidate search uses stored circles (original silhouette maximum radius × 1.20 + 0.05px), 64px spatial cells and 2px plus motion padding per ball. Registration computes radii once; candidate search builds no dense outline. Native unresolved pairs also reject by stored circles before exact silhouette queries. Existing cached contact resolution remains unchanged. Parameters: `broad_phase_radius_scale`, `broad_phase_cell_size` in the stage's physics Resource. The envelope is an approximation, not a new hard deformation constraint.

- Stage 61 composites gloss and nearby-ball reflections into the deforming outline shader. It hides the authored gloss without adding a reflection mesh. Reflection uses 96px cells over published ball positions and retains the best eight candidates in range. The solver keeps its separate 64px grid over predicted positions.

- The GDScript contact loop caches inverse masses, the contact denominator and the allowed approach distance per manifold and substep. It records an active contact once per substep and skips point writes for zero correction. Candidate search also caches each ball's speed per substep. Collision outline, iteration count and candidate order are preserved.

## Physics cost

With six controls, fixed-size outlines, two substeps and eight iterations, a tick costs approximately O(G + Q + N + P). N is the ball count, G is the number of ball-to-cell insertions, Q is the number of pair visits across cells before deduplication, and P is the number of surviving candidate pairs. For bounded cell coverage and occupancy this is approximately linear. A concentrated grid can still reach O(N²) time and memory. Inside each iteration, structure costs O(N × K²) for K controls, and cached contacts cost O(P × K). Unresolved pairs can rebuild outlines and convex hulls and run Godot's convex contact query again. The GDScript changes reduce repeated work per pair and keep the same worst-case order.
